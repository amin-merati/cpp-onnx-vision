# C++ ONNX Vision

A small C++17 image-classification inference runner, built as a portfolio
demonstration of model integration, memory ownership, numerical checks and
measurement. It loads an ONNX model, preprocesses an RGB image, runs inference
and writes top-5 class IDs and latency statistics as JSON.

**Status:** CPU implementation built and tested on Linux x86-64 with ONNX Runtime
1.20.1. Optional CUDA execution-provider selection is implemented but has not
been validated on GPU hardware. This is a new demonstrator, not a deployed
robotics system or a custom CUDA-kernel project. Developed with AI assistance.

## What it demonstrates

- RAII-based ONNX Runtime session management with explicit tensor lifetimes.
- Validated static float32 NCHW input and classifier-output contracts.
- Aspect-preserving resize, centre crop, RGB normalisation and planar layout.
- Sampling directly into the final tensor without allocating a resized image.
- Stable softmax, deterministic tie ordering and top-5 results.
- Warmup-separated median/p95 measurements and machine-readable output.
- C++ boundary tests and independent NumPy/Python inference comparisons.
- A GitHub Actions CPU workflow (supplied, not yet run on hosted GitHub).

The pretrained example is **SqueezeNet 1.1** from the ONNX Model Zoo. The much
smaller graph generated by the tests is a deterministic numerical fixture, not
a trained image classifier.

## Build and test

Supported quick-start environment: Linux x86-64, GCC/Clang with C++17, CMake
3.18+ and Python 3.12. Python is for setup, image conversion and tests; the
inference executable uses the ONNX Runtime C++ SDK directly.

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-dev.txt
python scripts/download_assets.py --model

cmake -S . -B build -DCMAKE_BUILD_TYPE=Release \
  -DONNXRUNTIME_ROOT="$PWD/deps/onnxruntime-linux-x64-1.20.1"
cmake --build build --parallel 2
ctest --test-dir build --output-on-failure

# Also compare the real classifier against Python on four image shapes.
python tests/reference_test.py --exe build/vision_infer \
  --work build/model-parity --model models/squeezenet1.1-7.onnx
```

The asset downloader checks SHA-256 digests before installing the SDK/model.
Downloads require internet access. If you already have a matching SDK, pass its
root to CMake instead. Models and SDK binaries are deliberately not committed.
The Python runtime version is pinned to match the C++ SDK for parity tests.

For a C++-only build, use `-DBUILD_TESTING=OFF`; Python is then unnecessary for
the build. CMake locates the shared runtime in the SDK and sets the build-tree
runtime path. This is a development build, not a relocatable binary distribution.

## Run an image

```bash
mkdir -p data
python scripts/to_ppm.py /path/to/photo.jpg data/photo.ppm
./build/vision_infer --model models/squeezenet1.1-7.onnx \
  --image data/photo.ppm --provider cpu --threads 1 \
  --warmup 10 --runs 100 --output result.json
```

`--help` lists all options. Input is binary PPM P6 with max value 255; the helper
converts JPEG/PNG and applies EXIF orientation first. Class IDs are zero-based;
map them using the model's own label order. Softmax scores are not calibrated
confidence estimates. The bundled example uses ImageNet's 1,000-class order.

## Model and preprocessing contract

- One float32 input of static shape `[1,3,S,S]`, with `1 <= S <= 2048`.
- One float32 logits output of shape `[1,C]` or `[1,C,1,...]`.
- Input RGB dimensions are limited to 8192 per axis; truncated rasters, extra
  trailing data and unsupported PPM encodings are rejected.
- Resize the short side to `round(S * 256 / 224)` and preserve aspect ratio,
  rounding the other dimension. Centre-crop to `S x S` with floor offsets.
- Bilinear sampling uses half-pixel coordinates and replicated image borders.
  Interpolation stays in floating point (no intermediate 8-bit rounding).
- Divide RGB values by 255, then normalise with mean `[0.485,0.456,0.406]` and
  standard deviation `[0.229,0.224,0.225]`. Write contiguous NCHW float32 values.

The contract is explicit so preprocessing can be reproduced. It is not a
drop-in implementation of every library's resize: there is no antialiasing
filter for downsampling, and integer rounding can differ. The tests validate
the implementation against its NumPy reference; they do not establish ImageNet
validation accuracy. Models with different preprocessing, dynamic batching,
multiple inputs, quantised tensors or dense detections need an adapter.

## Design and ownership

`image.cpp` owns parsing, preprocessing and numerical utilities. `Classifier`
owns the runtime environment, session and copied tensor names. The environment
outlives the session; input storage stays owned by the caller while `Run()`
uses a non-owning tensor view. Output logits are copied into an owning vector
before ONNX Runtime output values are destroyed. The caller reuses the
preprocessed input across measured iterations. Each run still allocates ORT
outputs and a logits vector: preallocated output/I/O binding is future work.

The CLI handles configuration, file I/O and measurement separately. PPM keeps
the C++ dependency surface small and makes byte-level preprocessing tests
straightforward. A production camera pipeline would use its native image
buffer format, timestamps and bounded queues rather than this file interface.

## Measurement

The JSON separates session creation from one image-read/preprocessing sample.
Warmups are excluded from inference samples. Each measured iteration includes
tensor-wrapper creation, synchronous `Session::Run`, output allocation and
the host logits copy; it excludes file loading, preprocessing, softmax, sorting
and JSON output. Percentiles use linear interpolation between sorted samples.
This is single-image latency, not video throughput or complete sensor-to-action
latency. Keep the input, model, thread count and runtime version fixed when
comparing changes.

An actual CPU sample is checked in at
[`benchmarks/cpu-squeezenet.json`](benchmarks/cpu-squeezenet.json), with its
environment and interpretation in [`benchmarks/README.md`](benchmarks/README.md).

## Optional CUDA provider

Use a compatible GPU-enabled ONNX Runtime C++ SDK and its required CUDA/cuDNN
dependencies, then rebuild with its path and pass `--provider cuda`. See the
[official compatibility table](https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html).
The supplied download script installs the **CPU** SDK only.

The executable errors if CUDA is unavailable or provider initialisation fails.
ONNX Runtime can still assign unsupported nodes to CPU; `requested_provider`
records the request, not proof that every node ran on GPU. Host I/O entails
transfers, included in the measured `Run()` path. No custom kernels, pinned
buffers, CUDA graphs, GPU speedup or GPU validation is claimed here.

## Checks

`core_tests` checks raster boundaries, normalisation/channel layout, stable
softmax, percentile interpolation and malformed inputs. `reference_test.py`
generates repeatable landscape, portrait, square and single-pixel inputs,
compares all preprocessed values with an independently vectorised NumPy
implementation, then compares C++ logits with Python ONNX Runtime outputs.
It also checks invalid CLI arguments, missing files and unsupported shapes.

```bash
# Optional diagnostics build. The prebuilt ORT library is not instrumented.
cmake -S . -B build-asan -DCMAKE_BUILD_TYPE=Debug -DENABLE_SANITIZERS=ON \
  -DONNXRUNTIME_ROOT="$PWD/deps/onnxruntime-linux-x64-1.20.1"
cmake --build build-asan --parallel 2
ASAN_OPTIONS=detect_leaks=0 ctest --test-dir build-asan --output-on-failure
```

## Scope and next steps

This project deliberately covers one complete classification path. Useful next
steps are GPU validation/profiling, reusable output buffers, label-file loading,
a detection model with explicit postprocessing, and a bounded live-camera
pipeline. A robotics deployment would also require failure handling, timing
budgets and validation on representative sensor data.
